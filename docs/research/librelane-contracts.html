LibreLane → RustLane

RustLane 应当是由 Rust 编写、可追溯和可恢复的 ASIC 流程执行器。综合由 RustSys 执行，时序分析由 RustSTA 执行；流程编排、设计状态和工具适配各有明确边界。

以下内容是对 LibreLane 公开契约的研究及 RustLane 的设计建议，并不表示已完成完整 RTL-to-GDS 实现或运行等价验证。

真正需要重建的是流程契约

LibreLane 把流程分成 Flow、Step、Configuration、State 四个概念。State 保存设计视图的路径及度量；Step 接收配置与输入状态，产生新的状态。SequentialFlow 按顺序连接这些状态。这个结构足以指导独立设计，无须移植 Python 类体系。

已验证配置+输入 State→有界 Step 执行→新 State 与收据

文档要求 Step 不原地修改输入文件、不修改输入配置，只使用配置和输入状态显式列出的文件，并把新产物写入自己的目录。随机过程需要固定种子。RustLane 可据此采用不可变产物、明确输入哈希和独立步骤目录。

来源：固定版 Architectural Overview。这是文档约束，未通过本次运行验证其全部实现行为。

边界LibreLane 的公开行为RustLane 的建议契约
配置JSON、YAML、Tcl 经验证后形成解析后的配置；流程变量由步骤变量汇集而成。先提供严格 JSON schema；未知语义、Tcl、表达式或未实现的条件键必须明确报错。保存完整解析结果和哈希。
设计状态不同格式分别保存，例如网表、SDC、DEF、GDS；多 corner 产物可以嵌套组织。格式、路径、内容哈希、corner 与生成步骤一并记录。工作区使用锁、base revision 和 mmap 侧表；句柄保持 shell 安全。
步骤输出每步目录保存配置、输入/输出状态、命令、工具日志、运行时间及资源统计。工具版本、可执行文件身份、argv、输入/输出哈希、退出码、wall time、峰值 RSS、诊断均进入收据。失败步骤不能推进成功状态。
恢复--from、--to、--skip、--only 配合输入状态快照控制执行区间。恢复前核验必需视图及哈希、配置、PDK 和引擎身份；缺少前序产物时拒绝执行。跳过步骤不能凭空生成成功度量。
复现resolved.json 可再次用于同一流程；步骤可生成问题复现包。固定 RustEDA 提交、工具与 PDK 修订、种子、线程数、corner、wire model 和预算；区分内容身份与机器路径/耗时等变化。
度量步骤更新 metrics，最终导出 JSON/CSV；时序报告按 IPVT corner 组织。缺少分析时记录 unchecked/unverified。时序必须含 corner、wire model、未约束端点，禁止用 0 表示未运行的 DRC 或时序结果。

来源：配置文档、迁移与输出文档、步骤目录和时序报告。RustLane 列为本项目建议。

Classic 流程的工作范围

固定提交的 Classic 声明包含从检查、综合、布局布线到签核的步骤。下面按产物归并；实际步骤还包括天线修复、断连检查、PDN 检查和可选优化。它们不能因为综合及 STA 已接通而被算作完成。

阶段输入 → 输出RustLane 实施边界
检查与综合RTL、Liberty、约束 → 映射网表及综合诊断使用 RustSys；不自动回退到 Yosys/ABC。转换正确性需 CEC 或黑盒差分证据。
布局前 STA映射网表、Liberty、SDC → 时序报告使用 RustSTA；显式说明 wire model，拒绝静默忽略约束或 Liberty 语义。
Floorplan / PDNLEF、网表、物理配置 → DEF、供电网络需要独立物理工具适配、PDK 技术层与单元视图；坐标为整数 DBU。
Placement / CTSFloorplan、网表 → 放置结果、时钟网络物理步骤单独建设；中间 STA 仍由 RustSTA 承担。时序驱动优化需要额外接口契约。
Routing / RCX布局与技术规则 → 布线 DEF、SPEF需要全局/详细布线器及寄生提取器；每个提取 corner 保存独立身份。
布局后 STA最终网表、SDC、Liberty、SPEF → 多 corner 时序使用 RustSTA；每个 corner 独立记录，验证增量与全量一致。
Stream-out / 签核物理结果与 PDK deck → GDS、DRC、LVS 报告需要实际流片格式与签核工具。未执行时保持 unchecked，不能声称已完成 RTL-to-GDS。

来源：Apache-2.0 Classic 步骤声明、公开 Classic 文档。只读取编排声明，未读取任何参考 EDA 引擎的实现源码。

Classic 不仅在开始与结束执行 STA：它在布局、CTS、布线期间反复执行中间 STA，并包含时序修复。仅替换前后报告不足以证明全部时序工作已使用 RustSTA。接入 OpenROAD 物理工具时，还需明确其内部时序驱动路径；未经确认的路径应保持未支持状态。

Sky130 与 GF180 必须同时进入验收

LibreLane 文档列出 Sky130 与 GF180 支持，默认 Sky130 单元库为 sky130_fd_sc_hd，GF180 的默认金属栈变体为 gf180mcuD。这些是 LibreLane 的兼容说明，并非本次对 RustLane 的 PDK 验证结果。

LibreLane 使用 Open PDKs 生成工具可用视图，并通过 Ciel 管理固定修订。手工 PDK 需要技术级和 SCL 级配置，以及步骤所需的额外变量。单独下载 Liberty 无法提供布图、RCX、DRC、LVS 和 stream-out 所需的全套数据。

来源：固定版 PDK 文档。该文档仍含“2.4/dev”旧文字；版本判断以本次固定提交的 pyproject.toml 3.0.16 为准。

验收项Sky130GF180
基础库sky130_fd_sc_hdgf180mcu_fd_sc_mcu7t5v0 或 gf180mcu_fd_sc_mcu9t5v0
综合固定 RTL、Liberty 与映射选项；RustSys 结果执行独立 CEC/黑盒检查；记录端到端时间和 QoR。
STA同一网表/SDC/Liberty/SPEF 下比较 RustSTA 全量、增量结果；与固定版本 OpenSTA 黑盒差分。逐 corner 报告误差和容限。
物理阶段核验技术/单元 LEF、GDS、RCX 规则、DRC/LVS deck 的实际存在及哈希；需要的 PDK Tcl 脚本不等于已支持的配置解析。
运行边界共享不可变解析库，限制 corner × 线程并发；每次大规模运行前估算内存，使用 cgroup/timeout、time -v；缺少工具或数据记录 unverified。

时序 corner 应保存 PVT 与互连 corner 的明确对应，不能根据文件名猜测。比如 SPEF 常按互连条件组织，Liberty 描述单元的 PVT 条件；两者需在运行配置中显式组合。

来源：Timing Corners。上表验收要求来自本项目 AGENTS.md；两种 GF180 SCL 均需使用实际取得的合法 PDK 数据验证。

下一步的具体完成标准

  1. 执行器：配置严格验证，工作区锁与 revision 冲突可测试；失败或超限不会提交成功状态；输出和输入不可变。
  2. 真实引擎：以 RustSys 和 RustSTA 的实际公开接口建立适配；保存实际输出，不以空报告或模拟后端充当分析成功。
  3. 恢复：引擎中断后可从已验证状态继续；输入、配置、PDK 或引擎身份变化会阻止无效重用。
  4. 正确性：综合通过独立 CEC，STA 通过全量/增量与双 PDK OpenSTA 差分；工具缺失与测试未覆盖分别列出。
  5. 物理流程：逐阶段接入真实产物及签核，验证后再声明对应阶段支持。端到端时间包含状态读写、数据准备及工具同步。

本次研究已回答流程结构、配置/状态/步骤契约、恢复与复现需求、Classic 阶段及双 PDK 接入条件。LibreLane 运行行为、RustLane 兼容性、实际 PDK 正确性、性能 QoR、DRC/LVS 和时序精度尚未由本次研究验证。
